- `prisma.config.ts` → migrations use `DIRECT_DATABASE_URL`, falling back to `DATABASE_URL`
- `package.json` → `build` is `prisma migrate deploy && next build`; `start` is plain `next start`. This matters: Vercel never runs `npm start`, so migrations must happen at build time.

## Important caveat about the migration

The Postgres migration has **never been run against a real database** — there was no local Postgres or Docker available to test it. The SQL is byte-identical to Prisma's own canonical output, so it should be correct, but the first `prisma migrate deploy` is the real test. If it fails, read the error carefully before changing the schema; the likely culprits are connection-string or permissions problems, not the DDL itself.

## Tasks

### 1. Provision Postgres

Use **Neon** (neon.tech) unless I say otherwise — free tier, and the free database doesn't expire. Vercel Postgres is fine too.

Get **both** connection strings:
- **Pooled** (host contains `-pooler`) → this becomes `DATABASE_URL`
- **Direct** (no `-pooler`) → this becomes `DIRECT_DATABASE_URL`

This split is not optional. Serverless functions open many short-lived connections and will exhaust a direct connection's limit; meanwhile Prisma Migrate needs advisory locks that a transaction-mode pooler cannot provide. Wrong URLs here produce confusing intermittent failures rather than clean errors.

### 2. Run the migration locally first

Before deploying, confirm the migration applies against the real database:

```bash

npx prisma studio   # confirm all 5 tables exist
```

Then run `npm run dev` and verify locally against Postgres: sign up with email/password, send a message to the AI Strategist, create a library entry. Do this **before** touching Vercel — debugging locally is far faster.

`SESSION_SECRET` must be identical across environments or existing sessions break. To generate a fresh one: `openssl rand -base64 32`.

### 4. Fix Google OAuth for production

The OAuth routes derive their redirect URI from `req.nextUrl.origin`, so they adapt to whatever domain they're served from — no code change needed. But Google must be told the new URI is allowed.

In Google Cloud Console → Credentials → my OAuth 2.0 Client, add to **Authorized redirect URIs**:
- `https://<vercel-deployment-url>/api/auth/google/callback`
- `https://www.mirrormemusic.com/api/auth/google/callback` (once the domain is live)
- Keep `http://localhost:3000/api/auth/google/callback` for local dev

Missing entries cause `redirect_uri_mismatch` at sign-in.
